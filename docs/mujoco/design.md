# Scene runtime and integration

**Status:** The scene engine, framed socket and package-owned P02 scene/device catalog are implemented. M1 graph-version readers exist in EOS and IsOS; IsOS P02 semantic admission, P03 option resolution, R05 strict socket and complete stop coordination remain separate work. Product release `0.1.1` does not make socket protocol `2.0.0` a product release.

The owner contracts are [package descriptor and contributions](interfaces/package.md), [MuJoCo-owned socket](interfaces/socket.md), and [benchmark RPC](interfaces/benchmark.md). This design describes the algorithms rather than redefining their payloads.

## Target activation algorithm

1. IsOS obtains the exact P01-verified package handle and checks the P02 scene profile, XML digest, device map, per-scene device support and external MuJoCo library. It passes only stable IDs and availability reasons to the later P03 option resolver. Package installation does not edit the graph.
2. The operator previews `sim-hardware`, chooses stable scene/device IDs, checks the draft and applies one revision. IsOS resolves verified paths in generated config; the graph keeps IDs and the exact package pin. A legacy `1.0.0` graph and `@v1.0` types remain readable; new authored graphs use `0.1.0` and newly registered types `@v0.1` after all readers support them.
3. EOS reads that revision without editing it, selects the compiled internal `mujoco-v2` adapter factory, and starts the verified simulator as its direct child with the R05 managed strict launch flag. The child cannot advertise `strict-socket-v1` until strict checks and historical gRPC actuator-listener suppression are active. EOS requires the strict health feature for every declared device before publishing readiness. Failed health or a mismatched device keeps the node unavailable and is logged with `run_id`, optional `node_path` and `correlation_id`.
4. The dispatcher admits each actuator command before the adapter sends it. EOS verifies graph node, device kind, scene and package pin; the simulator validates the exact device/operation pair and finite scene bounds, then deduplicates `(node,command_id)` to protect identical bounded transport retransmission. EOS never replays an uncertain released command automatically. The R06 dedicated stop lane and separate base/arm acknowledgment remain required before safe-stop qualification.
5. On shutdown EOS closes command admission, requests stop for every admitted actuator with a bounded deadline, records any missing acknowledgment, then terminates and reaps its child. IsOS reports deployment stopped only after EOS exits or a bounded forced-stop path is recorded. The simulator removes owner-only sockets on normal exit.

## P02 catalog construction and compatibility

The bundle builder retains the authored stable scene IDs, derives their digests from packaged XML bytes, and cross-checks the device catalog against the engine-supported camera, base and arm model elements. A deterministic fixture pins the expected profile markers, all three device IDs and the package-owned process type. A build or candidate bundle fails when a declared marker differs from the sole marker in the XML, when a model lacks an element required by a declared device, or when a scene or device ID duplicates another. Real MuJoCo engine load and replay tests establish that these XML files remain usable; XML catalog checking alone does not establish model compatibility.

IsOS will first use P01 receipt verification and path containment, then parse the exact verified descriptor. The exact `catalog_version:"0.1.0"` discriminator requires complete scene and device metadata; its absence requires the complete legacy shape. A partial mix fails before any option is published. IsOS compares the selected scene ID with its declared profile and XML hash, checks the chosen device ID against the kind and scene, and checks the external library before graph publication or spawn. It reports unavailable choices for a repairable draft and rejects an unavailable selected value at Apply with the contract's stable `{code,path,stage}` diagnostic. It repeats verification on Run and Restart; a changed linked payload requires explicit relink and cannot quietly update the running graph. A scene edit uses IsOS revision compare-and-swap and reaches EOS only after a new saved revision is restarted.

The new `sim-hardware` preset contains seven nodes in the EOS core and relies on the dispatch-control node already in the IsOS starter. Its hardware nodes are generic EOS `@v0.1` registrations with an exact package-pinned `mujoco-v2` adapter. Only the process type is contributed by MuJoCo. Previously verified legacy sidecars remain readable for old graph behavior; neither a legacy `@v1.0` type nor an unregistered IsOS Vision type is placed in the new preset. P03 owns generic `(node_path,setting)` option grouping and UI echo. R05 owns the managed socket's device/operation checks; the present socket ignores `node`, so P02 metadata alone cannot certify command routing. See the [P02 package contract](interfaces/package.md#p02-descriptor-extension) and [frozen fixtures](../../tests/fixtures/scene_catalog/README.md).

The design review fixture check parses the four JSON fixtures, verifies the target/legacy discriminator shapes and frozen diagnostic tuples, hashes both repository scene XML files, checks each declared profile marker and device/scene relation, and validates relative Markdown links. ## Target command and log algorithms

**R05 target design — not implemented.** The [socket contract](interfaces/socket.md) owns the exact flag, health fields, bounds, errors and retention. IsOS generated config selects a verified package and scene for an EOS-managed launch. EOS derives `--managed-strict-socket` from that managed launch, not from a graph-writable setting. In strict mode the simulator rejects both historical gRPC `SimulatorService` and benchmark socket arguments. `SimulatorService.Execute` would otherwise be a second actuator route outside Dispatcher, while benchmark Reset/Step could change the same engine state. A trusted evaluator uses a separate direct launch. Direct launches without the flag preserve the existing legacy framed, gRPC and benchmark behavior under wire `2.0.0`.

Strict readiness is an end-to-end check, not a successful connect. EOS probes health on each graph-declared scene device and checks protocol version, echoed request ID, positive `ok` and `accepted`, and `strict-socket-v1` in the response feature list. The simulator binds its strict framed listener only after it can enforce exact device/operation matching, finite typed movement limits, and bounded IDs. EOS refuses and reaps a child that omits or contradicts the feature. The current `BackendChild::wait_ready` checks only socket connect, and the current adapter health accepts any successful health reply; both are R05 implementation seams.

For a valid motion or `stop`, the server reserves `(node,command_id)` before calling the engine and stores a canonical typed-operation fingerprint and result for the whole child generation. An identical transport retransmission gets the prior result with the new transport request ID; a conflict gets `command_id_conflict`. Concurrent duplicates cannot release twice. Fixed movement and reserved stop capacities reject new commands rather than evicting a key; no TTL expiry may permit same-child replay. This bounded in-process retention does not replace the EOS durable Dispatcher journal: after a disconnect, timeout or restart, an uncertain released command remains unknown, and EOS reconciles from fresh observations or requires a new explicit admission. The current server ignores both `node` and `command_id` and serially accepts connections; R05 does not claim stop preemption. R06 must add the dedicated bounded stop lane and dual acknowledgments before child termination/reap may be called safe.

Emit a sanitized JSONL event once for startup identity (package, scene ID, protocol and `run_id`), then on readiness changes, command admission/result, socket failures and shutdown. Do not log image bytes, arbitrary environment values or all high-rate observations. A first-use reader starts at the current run's first ready/failure event, then filters by canonical `node_path` and `correlation_id`. The shared event shape, rotation and cursor reading are defined by IsOS; this package supplies source `mujoco` and its own event codes.

**R05 design evidence:** [31 frozen cases](../../tests/fixtures/strict_socket/cases.json) cover direct-launch compatibility, strict launch isolation, health proof, device/operation matching, typed bounds, duplicate/conflict/capacity, malformed frames and EOS no-replay. On 2026-11-02, `python3 tests/fixtures/strict_socket/check.py`, `python3 tests/scene_catalog.py`, `python3 tests/node_contributions.py`, `python3 tests/release.py` and `git diff --check` passed; complete output and commands are in ignored `logs/test/20261102-r05-strict-design/design-check.log`. These validate design fixtures and existing catalog/release behavior, not the pending strict socket runtime implementation.

One simulator process loads one scene profile at startup. Its engine owns MuJoCo model and data, deterministic seeded reset, fixed-step physics, robot command targets, telemetry, camera rendering, and scene-specific scores. The EOS-facing service and the benchmark service share that engine, but publish different information. The simulator socket returns device health, command outcomes, telemetry, and camera JPEGs. The benchmark socket lets a trusted evaluator reset or step the world and inspect ground truth and scores.

Direct launch uses `--scene`; an IsOS/EOS v2 deployment selects the scene in its applied shared graph and EOS passes that path to its simulator child. The selected MJCF declares exactly one supported custom numeric marker, `eos_benchmark_pick_place_v1` or `eos_benchmark_navigation_v1`; an unknown or multiple benchmark markers are rejected. The engine then checks required named elements, including `navigation_goal` for the navigation profile. A different XML file is not automatically an admitted benchmark; each profile needs explicit reset and scoring logic, documented capabilities, and tests. Changing a scene requires a process restart.

The simulator still exposes the legacy `eos.simulator.v1.SimulatorService` gRPC socket for older direct integrations. The current IsOS/EOS v2 runtime connects generic camera, base, and manipulator adapters to the separate owner-only framed socket selected by `--v2-socket`; its contract is in [backend.md](backend.md). EOS owns the simulator child and exposes graph-declared observation and primitive ports to agents. The benchmark socket remains separate from both robot-facing interfaces. This package does not link into EOS core.

EGIA attaches to an already-running EOS gateway, discovers its healthy devices and versioned primitives, and executes through EOS. It does not receive benchmark seed, goal truth, privileged state, or score. EGIA fleet aliases identify EOS endpoints; the simulation scene remains EOS's configuration choice. Agent evaluation compares an EGIA or other agent's EOS-visible behavior with a separate evaluator's private result.

The published v1.0.1 package and its generated EOS profile belong to the legacy route. For v2, IsOS links or installs an exact `island/mujoco-sim@0.1.1` bundle, verifies its executable, scene, assets, and external MuJoCo library, and applies a shared graph revision through the `sim-hardware` node set. EOS reads that graph and starts the verified simulator as its direct child. A source build may still run directly with absolute scene and socket paths.

## Timing and failures

MuJoCo advances in fixed 2 ms physics steps. A reset sets a deterministic seeded initial state and pauses real-time stepping. The evaluator can advance a bounded number of steps, inspect state, score, and resume live stepping. Repeatability requires the same scene version, seed, command sequence, and stepping schedule; asynchronous real-time observation is not a deterministic replay contract.

Startup fails for a missing or invalid scene, missing required scene elements, or an unusable socket. Unavailable or unsupported devices and commands fail through the EOS-facing service. The benchmark service reports reset or step errors in `StateResponse.ok` and `error`. Ground-truth fields that are irrelevant to a scene should not be used as an agent input or inferred as a goal.
