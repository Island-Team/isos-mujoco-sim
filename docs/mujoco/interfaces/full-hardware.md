# Full robot hardware package (next release candidate)

The next `island/mujoco-sim` release contributes seven EOS hardware type definitions and **Native robot** and **RoboCasa robot** device presets. Each instance pins the exact package both as its type owner and as its adapter owner. The types live in the EOS hardware layer under camera, base, manipulator, gripper, and torso groups; other packages may choose different layers and groups. A preset contains no process node. IsOS starts only the package service referenced by selected nodes, owns its child and logs, and passes a private service endpoint to EOS. EOS loads the verified `libmujoco-eos-node.so` through `isos_node_v2` and admits actuator commands through its Dispatcher.

The native preset exposes `cam-0`, `base-0`, `arm-0`, and `gripper-0`. Its strict socket supports JPEG capture, SI base state/twist, six-joint state/position, gripper opening/close, generation-fenced commands, and whole-robot stop proof with separate base, arm, and gripper outcomes. The gripper observation has a named `opening` channel in percent. The scene is `pick-place` or `navigation`; the package's verified scene resource supplies the path.

The RoboCasa preset exposes three RGB8 cameras, mobile base, right arm, right gripper, and torso. Its Python Gym environment runs in an IsOS-owned child with bytecode writes disabled, preserving the verified package bytes; EOS never loads Python. Its observation timestamps use the declared `monotonic` host clock. The base pose is in the world frame; the end-effector pose is relative to `robot_base`; both quaternions are `xyzw`. The two Panda gripper slide-joint channels are metres. The worker serializes steps, deduplicates command IDs within the generation, and rejects further control after a step failure. Stop fences queued commands, clears motion and mode state, and steps neutral motion until the latched gripper channels are stable. The service caches that run-bound result so every selected actuator can receive the same proof; a failed step or unstable gripper reports `unknown`. The torso has no fabricated position observation. Benchmark reward and success are never exposed as hardware data.

`config/package-config.json` declares bilingual labels and descriptions for the generic IsOS package form. `config/package.toml` provides `[package]`, `[host]`, `[services.native]`, and `[services.robocasa]`. A selected native service needs a local MuJoCo 3.3.1 root. A selected RoboCasa service needs local assets and an explicitly selected Python interpreter. These large host resources are not downloaded with the release. Their paths are local deployment configuration, not graph node settings. Every hardware adapter setting selects a `service_instance`; IsOS resolves that instance at Apply and Run.

The RoboCasa service configuration also requires integer `camera_width` and `camera_height` in `[services.robocasa]`. Both default to 64 in the template and must be 64–512 pixels. The verified service handoff passes them as `ISOS_ROBOCASA_CAMERA_WIDTH` and `ISOS_ROBOCASA_CAMERA_HEIGHT`; the worker validates both before creating the Gym environment and uses the resulting dimensions for all three camera observations. A changed size takes effect on the next Run. The installed `0.2.2` package retains its fixed 64 × 64 behavior; use a new package version, import its updated configuration, and repin the graph to enable this field.

The RoboCasa worker's private `observe` reply carries camera dimensions in `width_px` and `height_px` metadata and exactly `width_px × height_px × 3` RGB8 bytes in the socket payload. Metadata remains bounded to 64 KiB and the payload to 8 MiB. State observations keep their JSON `values` response. The plugin verifies the exact dimensions and byte count before emitting the graph's typed frame.

Build the candidate with `./build.sh --output ABSOLUTE_EMPTY_DIRECTORY --version 0.2.3` or a later unused version. The published v0.2.0, v0.2.1, and v0.2.2 tags remain unchanged. A candidate is publishable only after the IsOS `pkg check` replay succeeds for both presets, including rejection, crash, logs, and Stop cases.

On 2026-11-13, the `0.2.3` source candidate passed isolated `isos pkg check` with the EOS command acknowledgment fix from IsOS PR #504. Run `isos pkg check --source <this checkout> --version 0.2.3 --output <empty evidence directory> --graph <RoboCasa full-preset graph pinned to 0.2.3> --graph <native full-preset graph pinned to 0.2.3> --package-config <local package.toml>` with `ISOS_AETHER_BIN_DIR` pointing to the corrected EOS binaries and the normal local EI and MuJoCo host paths set. The 256 × 192 and 512 × 512 configurations each passed static verification, native ABI, owner admission, managed observation/control/logs, and confirmed Stop for both presets. All three RoboCasa camera frames reported the requested dimensions. The exact commands, inputs, `check.json`, owner exchanges, and complete build logs are retained under ignored `data/test/2026-11-13-camera-size/`; the candidate archive SHA-256 is `58e3d9fa8d45345d5fe9a0da5f804d016bc6fbddbcb08fcceeece32d92c0bf6f`. Publication and graph repinning remain separate operator actions.
